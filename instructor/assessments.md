# Assessments

Everything used to judge progress in this course: a diagnostic to take before starting,
one milestone per part with acceptance criteria and a rubric, an end-of-part assessment
for each part, and the final checklist of abilities.

The course is **mastery-based**. A module is complete when its mastery criteria (end of
each `quiz.md`) are met; a part is complete when its milestone is accepted. Running the
commands is not the criterion. Understanding is, and it is shown by predicting results
before measuring them, by explaining measured results, and by finding what is wrong with
a wrong one.

Rubric levels used throughout (details in [grading-rubrics.md](grading-rubrics.md)):
**not yet** · **developing** · **proficient** · **exemplary**. "Proficient" on every row
is the standard for acceptance.

## Baseline diagnostic

Take this before Module 01, closed book, in about 45 minutes. It is not graded. Its
purpose is to choose a starting point and a track ([LEARNING_PATHS.md](../LEARNING_PATHS.md)).
Score one point per item answered confidently and correctly; the answer key follows.

**A. Mathematics and classical networks**

1. Compute the matrix product $\begin{pmatrix}1&2\\0&1\end{pmatrix}\begin{pmatrix}3\\4\end{pmatrix}$ and state the shapes involved.
2. $f(x) = \sigma(wx + b)$ with the logistic function $\sigma$. Give $\partial f/\partial w$.
3. What does the softmax function do to the vector $(2, 2, 2)$? To $(10, 0, 0)$, approximately?
4. A classifier assigns probability 0.25 to the correct class. What is its cross-entropy loss in nats and in bits?
5. In backpropagation through a two-layer network, which quantities from the forward pass must be kept, and why?
6. What is the difference between a training set, a validation set and a test set?

**B. Programming**

7. In NumPy or PyTorch, what is the shape of `x @ y` for `x` of shape `(8, 16, 32)` and `y` of shape `(32, 4)`?
8. What does broadcasting do when a tensor of shape `(8, 1, 32)` is added to one of shape `(16, 32)`?
9. What does `loss.backward()` compute and where does it put the result?
10. You run the same training script twice and get different numbers. Name two possible reasons.

**C. Language models (expect to miss some: these are what the course teaches)**

11. What does an autoregressive language model predict, and how is text generated from it?
12. What is a token, and why are tokens usually neither characters nor words?
13. What problem does the attention mechanism solve that a fixed-size hidden state does not?
14. Why does a Transformer need information about token positions?
15. What does "temperature" change when sampling from a model?
16. What is the difference between pretraining and fine-tuning?
17. What is a KV cache for?
18. What is the difference between a model using a tool and a model computing an answer itself?

**Answer key**

1. $(11, 4)^\top$; a $2\times2$ matrix times a $2\times1$ vector gives $2\times1$.
2. $\sigma(wx+b)\,(1-\sigma(wx+b))\,x$.
3. $(\tfrac13, \tfrac13, \tfrac13)$; approximately $(1, 0, 0)$ (the others about $4.5\times10^{-5}$).
4. $-\ln 0.25 = 1.386$ nats $= 2$ bits.
5. Each layer's input and pre-activation (or activation): the gradient of a layer's weights is the product of its input and the error signal arriving from above, and the derivative of the non-linearity is evaluated at the stored value.
6. Training: used to fit parameters. Validation: used to make choices (hyperparameters, early stopping). Test: used once to estimate performance on unseen data after all choices are made.
7. `(8, 16, 4)`.
8. The shapes are aligned from the right: `(8, 1, 32)` and `(1, 16, 32)` broadcast to `(8, 16, 32)`.
9. The gradient of `loss` with respect to every tensor that requires gradients, accumulated into each tensor's `.grad`.
10. Unseeded randomness (initialisation, data order, sampling); non-deterministic parallel or GPU kernels; different software versions or hardware; a changed data file.
11. A probability distribution over the next token given the preceding ones; text is generated by sampling a token, appending it and repeating.
12. A unit of the model's vocabulary, typically a frequent piece of text (sub-word). Characters make sequences long and words make the vocabulary unbounded; sub-words are a compromise that can represent any text.
13. It lets each position read directly from any earlier position, with learned, content-dependent weights, instead of squeezing all history through one vector.
14. Attention by itself treats its inputs as a set: without positional information, "dog bites man" and "man bites dog" would look the same.
15. It rescales the logits before the softmax: low temperature concentrates probability on the most likely tokens, high temperature flattens it.
16. Pretraining: next-token prediction on a large general corpus. Fine-tuning: continued training on a smaller, specific data set to change behaviour (e.g. to follow a chat format).
17. It stores each layer's keys and values for the tokens already processed, so that generating a new token does not recompute the whole sequence.
18. With a tool the model writes a request that ordinary code executes, and uses the returned result; the correctness of the computation comes from the code, not from the model's weights.

## Milestone 1

**Part I. Build, explain and train a minimal causal Transformer.**

Deliverables, in a directory of your choice (suggested: `results/runs/milestone-1/`):

1. A trained MiniGPT on Pocket (`labs/foundations/07_train_minigpt.py`, or your own script using `mlle.foundations`), with its training log and configuration.
2. Generated samples, with the fraction that are valid Pocket sentences.
3. A written explanation (2–4 pages) of the forward pass of your model for one short input, with tensor shapes at every step, from token ids to loss.
4. A table mapping every component of your model to the corresponding lines of nanochat at the pinned revision, including at least five differences.
5. The result of one ablation you chose (for example: no positional information, one layer instead of two, no residual connections), with a prediction written before the run.

**Acceptance criteria**

- [ ] Final validation loss within 0.03 nats/char of the entropy floor (0.3139), or an explanation of why your configuration cannot reach it.
- [ ] `tests/test_minigpt.py` passes in your environment; the nanochat parity lab (`labs/foundations/06_nanochat_parity.py`) reports agreement.
- [ ] The explanation is correct in every tensor shape and can be followed without the code.
- [ ] The ablation has a stated prediction, a result, and an interpretation that would survive a second seed (or you ran one).

| Rubric row | Proficient | Exemplary |
|---|---|---|
| Correctness | model trains to near the floor; tests pass | also reproduces a nanochat logit vector through the bridge and explains each neutralised extra |
| Explanation | every step and shape right | derives one gradient by hand and checks it numerically |
| Mapping to nanochat | all components located, five differences | explains *why* nanochat differs for three of them, with evidence from the source or its log |
| Experiment | prediction, single variable, interpretation | several seeds; states what the experiment cannot show |

## Milestone 2

**Part II. Train and evaluate a small nanochat model; investigate one variable.**

Two versions, by hardware. **CPU version**: the miniature pipeline on Pocket
(`make nanochat-local-data nanochat-local-train nanochat-local-eval`). **GPU version**: a
depth chosen with `scripts/experiments/estimate_run.py` from a throughput measured with a
probe (`make spark-probe` on a DGX Spark).

Deliverables:

1. The exact commands, the checkpoint metadata file, and the training log.
2. A results record ([template](../results/templates/experiment-record.md)): validation bits per byte with the comparison to the entropy floor (CPU version) or CORE with its uncertainty (GPU version); samples.
3. A sizing table made *before* the run: parameters, training tokens, steps, predicted duration from measured tokens per second; and the actual duration afterwards.
4. One controlled experiment with a single variable (for example: depth, the data-to-parameter ratio, sequence length, a duplicated or contaminated data shard), with a prediction.

**Acceptance criteria**

- [ ] The run is reproducible from the record alone.
- [ ] Predicted and actual duration are both reported; a discrepancy above 30 % is explained.
- [ ] Every number is labelled measured, reported or estimated, and no upstream 8-GPU figure is used as a prediction for your machine.
- [ ] The experiment changes one variable, reports the noise level (at least two seeds, or a justified reference to measured seed variance), and draws a conclusion the data support.

| Rubric row | Proficient | Exemplary |
|---|---|---|
| Reproducibility | commands, revision, configuration, seed recorded | a second person reproduced it |
| Sizing | prediction made in advance and compared | includes a memory prediction and a break-even analysis for compilation |
| Evaluation | correct metric, uncertainty stated | compares with a baseline (n-gram or smaller model) and explains the gap |
| Experiment | one variable, noise considered | pre-registered prediction; replicated |

## Milestone 3

**Part III. A reproducible benchmark suite comparing baseline and optimised approaches.**

Deliverables:

1. The output of `make bench` on your machine, three times, with the manifest (`results/runs/benchmarks.jsonl`).
2. One comparison you added yourself (lab 13, Exercise 5.2), with a correctness or quality column.
3. A report (2–3 pages): for each optimisation, the resource it targets, whether it is exact, the measured effect with its run-to-run variation, and whether you would enable it on your hardware.
4. *(GPU, optional)* `python -m scripts.infer_bench` on a nanochat checkpoint, with the batch sweep interpreted.

**Acceptance criteria**

- [ ] Every row has a correctness or quality column, and every exact optimisation is verified by equality to rounding.
- [ ] Timings are reported with their variation over at least three runs; no claim rests on a difference smaller than that variation.
- [ ] Sequence length, batch size, model size, precision and hardware are stated for every number.
- [ ] The report distinguishes exact from approximate optimisations and evaluates the latter with a quality metric.

| Rubric row | Proficient | Exemplary |
|---|---|---|
| Correctness discipline | equality tests for exact methods | finds and documents a configuration where an "exact" method differs, and explains it |
| Measurement | warm-up, synchronisation, repetitions | separates prefill from decode; reports a bandwidth or FLOP bound next to the measurement |
| Interpretation | names the binding resource | predicts how each result changes on a GPU and tests one prediction |
| Own comparison | runs and is documented | reveals something the standard suite does not |

## Milestone 4

**Part IV. From base model to assistant, with controls.**

**CPU version** (the course's world): labs 14a, 14b, 15a, 15b. **GPU version**:
`scripts.chat_sft` on your Milestone 2 model, evaluated with `scripts.chat_eval`, plus a
short `scripts.chat_rl` run if time allows.

Deliverables:

1. The five-row table of lab 14a from your own run, with a written attribution: what pretraining contributed, what fine-tuning contributed, what was forgotten.
2. One fine-tuning variation of your own (data size, replay, LoRA configuration, a masking change), with a prediction.
3. The three runs of lab 15a from your own run, and a one-page analysis of the flawed-reward run: what was optimised, what happened to the true objective, and how you would have detected it without knowing the truth.
4. A demonstration that the improvement in run A is a change in the *weights* and not a prompting effect: the same prompts, before and after, with the checkpoint as the only difference.

**Acceptance criteria**

- [ ] Chat accuracy is reported on held-out problems, separately from problems seen in fine-tuning.
- [ ] At least one retained-capability measurement accompanies every fine-tuning result.
- [ ] The reward-hacking analysis identifies the mechanism, not only the symptom.
- [ ] Reward-driven improvement is shown with the evaluation independent of the reward.

| Rubric row | Proficient | Exemplary |
|---|---|---|
| Controls | both controls of lab 14a present and interpreted | adds a control of your own design |
| Forgetting | measured and reported | compares two mitigation strategies |
| RL | improvement shown with an independent evaluation | reports sensitivity to learning rate or samples per prompt, with a stability observation |
| Analysis of failure | mechanism of the hack explained with examples | designs and tests a different flawed reward |

## End-of-part assessments

Open book, your own work, 60–90 minutes each. Each has three kinds of question:
*explain*, *predict-then-check* and *find the flaw*. Answers are assessed with the
[conceptual-explanation rubric](grading-rubrics.md#rubric-1-conceptual-explanations).

### Part I — Foundations

1. **Explain.** Trace one token through a nanochat-style block: which operations read from other positions, which act on each position alone, and where position information enters.
2. **Explain.** Why does a causal model trained on $T$ positions of a row receive $T$ training signals from one forward pass?
3. **Predict, then check.** In MiniGPT, block the attention edge from the last position to the subject of a Pocket sentence (`blocked_edges`). Predict the effect on the verb's probability; measure it.
4. **Predict, then check.** Double the learning rate of your Milestone 1 run and halve it. Predict the order of the three final losses.
5. **Find the flaw.** "Our model reaches a validation loss of 0.29 nats per character on Pocket." (The entropy floor is 0.3139.)
6. **Find the flaw.** "Attention head 2.1 attends to the previous token, so it implements bigram statistics."

### Part II — Training language models

1. **Explain.** What is in a row of a nanochat training batch, and why does every row begin with BOS?
2. **Explain.** Why is bits per byte comparable across tokenizers while loss per token is not?
3. **Predict, then check.** With `scripts/experiments/estimate_run.py`: how do parameters, training tokens and total FLOPs change from depth 12 to depth 16? Predict the ratios before running.
4. **Predict, then check.** Evaluate your Milestone 2 model with 100 and with 500 items per task (or, on CPU, with 20 and 200 evaluation batches). Predict how much the score will move.
5. **Find the flaw.** "Model B is better: its validation loss is 0.004 lower." (One run each.)
6. **Find the flaw.** "We removed duplicates from the training set and the validation loss went up, so deduplication hurts."

### Part III — Performance engineering

1. **Explain.** Why is decoding at batch 1 limited by memory bandwidth and prefill by arithmetic?
2. **Explain.** Why do master weights stay in fp32 when computation is in bf16?
3. **Predict, then check.** KV-cache bytes for your model at 1 024 tokens; then measure the allocation.
4. **Predict, then check.** Peak memory of a training step when the batch is halved and accumulated twice.
5. **Find the flaw.** "Our tiled attention is 20 % faster than the baseline." (No correctness column, one run.)
6. **Find the flaw.** "The model with a sliding window has the same validation loss, so the window costs nothing."

### Part IV — From base model to assistant

1. **Explain.** Which tokens of a conversation are training targets, and what goes wrong for each category if the rule is broken?
2. **Explain.** Derive the policy gradient and explain why a prompt whose samples all receive the same reward teaches nothing.
3. **Predict, then check.** Fine-tune with 300 instead of 3 000 conversations. Predict chat accuracy on held-out problems.
4. **Predict, then check.** Run the flawed-reward experiment with a learning rate three times larger. Predict what happens to reward and to accuracy.
5. **Find the flaw.** "After fine-tuning, accuracy on our task rose from 0 % to 88 %, which shows fine-tuning taught the model arithmetic."
6. **Find the flaw.** "The DPO loss fell from 0.69 to 0.03, so the model now prefers the better answers."

### Part V — Reasoning, tools and agents

1. **Explain.** Why can a model fail to compute in one pass what it computes easily when it writes intermediate steps?
2. **Explain.** Why can prompt injection not be solved inside the model, and where must the defence sit?
3. **Predict, then check.** A model with 10 % per-step errors on a 12-step task: predict success with and without the loop's validation, then measure with the simulated policy.
4. **Predict, then check.** Voting with 15 samples when half the errors are systematic.
5. **Find the flaw.** "Our three-agent system scores 94 %; the base model scores 53 %."
6. **Find the flaw.** "The reviewer agent approved 97 % of the answers, so quality is high."

### Part VI — Integration

1. **Explain.** Name the two artefacts every stage must share exactly, and a symptom of each mismatch.
2. **Explain.** What does retrieval fix, and which three conditions must a retrieval system be tested under?
3. **Predict, then check.** Which fields differ between two manifests of the same seed? Of different seeds?
4. **Find the flaw.** "The new architecture uses 30 % fewer FLOPs, so it trains 30 % faster."
5. **Find the flaw.** "We added retrieval, so the assistant can no longer give outdated answers."

**What the "find the flaw" items test** (for self-assessment): Part I: a loss below the
entropy floor signals leakage or a measurement error; an attention pattern is not a
mechanism without an intervention. Part II: a difference below seed noise; a validation
set contaminated by the duplicates that were removed from training. Part III: no
correctness check and no variance; an average metric that cannot see a lost long-range
capability. Part IV: no control for knowledge already present; a loss on differences that
can fall while the preferred answer becomes less likely. Part V: unequal cost and the
wrong baseline; a reviewer that shares the author's blind spots. Part VI: FLOPs are one
of three resources; retrieval replaces staleness by dependence on the retriever and the
corpus.

## Final checklist of abilities

At the end of the course you should be able to do each of the following without
assistance. Tick an item only after you have actually done it.

**Explain**

- [ ] Explain, to a programmer who knows classical neural networks, what a Transformer language model computes, from text to next-token probabilities, with tensor shapes.
- [ ] Explain why attention, residual connections, normalisation and positional information are each present, with an experiment that shows what happens without one of them.
- [ ] Explain the training objective, what the loss number means in bits, and what its floor is.
- [ ] Explain where the time and memory of training and of inference go, and which hardware limit binds in each phase.
- [ ] Explain how a base model becomes an assistant, and what fine-tuning cannot add.
- [ ] Explain what a tool call, a reasoning trace and an agent are, in terms of tokens, code and loops.

**Build**

- [ ] Implement a causal Transformer, its training loop and a KV cache from an empty file, and test them.
- [ ] Render conversations with a loss mask and fine-tune a model on them.
- [ ] Implement a policy-gradient update for a language model.
- [ ] Build a tool-using loop with validation, permissions, budgets and a trace.
- [ ] Build an experiment loop with a ledger, a noise threshold and a held-out test.

**Operate nanochat**

- [ ] Find, in the pinned source, the lines that implement any mechanism of Parts I–IV.
- [ ] Size a run before starting it, from measured throughput, and state the estimate's uncertainty.
- [ ] Train, evaluate, fine-tune and benchmark a model on your hardware, with a record another person can reproduce.
- [ ] Diagnose a failed or slow run from its log.

**Judge**

- [ ] Distinguish measured, reported and estimated numbers in your own writing and in others'.
- [ ] Decide whether a difference between two results is larger than the noise.
- [ ] Identify the missing baseline or control in a claimed improvement.
- [ ] Recognise reward hacking, validation overfitting and shared blind spots in a described system.
- [ ] Read a new paper or repository with the seven questions of Module 22 and say what you would need to see before adopting it.

A learner who can tick every box has reached the course's goal: not familiarity with a
code base, but the ability to reason about, build, measure and criticise language-model
systems.
